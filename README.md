# Цифровая визитка

Backend-приложение на NestJS отдаёт профиль, навыки, опыт работы и проекты через GraphQL. Схема доступна в Apollo Sandbox.

## Запуск

Нужны Docker и Docker Compose.

```bash
docker compose up --build
```

Sandbox открывается по адресу http://127.0.0.1:3000/graphql.

На Windows `localhost` часто указывает на IPv6-адрес `::1`, а Docker публикует порт на IPv4. Поэтому в браузере нужен именно `127.0.0.1`.

Пример запроса:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

При первом запуске Postgres пустой. Контейнер приложения применяет миграции и записывает данные визитки. Повторный запуск вторую копию профиля не создаёт. Полный сброс вместе с данными:

```bash
docker compose down -v
```

Публичный экземпляр развёрнут на Render: Web Service собирается из `Dockerfile`, PostgreSQL создан отдельным сервисом в том же регионе. Адрес базы передаётся переменной `DATABASE_URL` и в репозиторий не входит.

## Архитектурные решения

### Разделение ответственности

Приложение собрано из двух модулей Nest.

`PrismaModule` только открывает и закрывает соединение. `PrismaService` наследует клиент Prisma и читает `DATABASE_URL` через `ConfigModule`. Бизнес-данных в этом модуле нет.

`ProfileModule` содержит три разные задачи:

- `profile.data.ts` хранит содержимое визитки;
- `ProfileSeedService` записывает его в пустую базу при старте;
- `ProfileService` читает таблицы;
- `ProfileResolver` превращает эти данные в ответ GraphQL.

Резолвер не обращается к Prisma напрямую. Сервис не знает, как устроен HTTP-запрос.

### Модель данных

Визитка описывает одного человека, поэтому все записи принадлежат одной строке `Profile`. Навыки, ссылки, места работы и проекты связаны с ней внешним ключом. Удаление профиля удаляет связанные строки (`ON DELETE CASCADE`): отдельно от профиля они не существуют.

Ссылки вынесены в таблицу `Link`, а не в фиксированные поля `github` и `linkedin`. В задании перечислены GitHub, LinkedIn и другие профессиональные ресурсы, набор ссылок может меняться.

Достижения хранятся массивом строк `TEXT[]` у конкретной работы. Отдельная таблица не нужна: достижение не запрашивается само по себе и не связано ни с чем, кроме одного места работы.

Поле `sortOrder` задаёт порядок на визитке. Дата начала работы для этого не используется: записи могут идти в порядке, удобном для чтения, а не в хронологии вставки.

Идентификатор — целое число с автоинкрементом. Записей мало, они создаются в одной базе, а номер легко увидеть в Sandbox. UUID имел бы смысл, если бы идентификаторы выдавались несколькими независимыми сервисами до записи в общую базу.

Пустая `endDate` означает текущее место работы.

### PostgreSQL

База реляционная: у профиля много навыков, мест работы и проектов. PostgreSQL выбран потому, что тот же тип базы используется локально в Docker Compose и на Render. Отдельная файловая база упростила бы первый запуск, но её пришлось бы менять при упаковке в контейнеры.

### GraphQL

Схема описывается классами TypeScript (code-first) и при старте записывается в `src/schema.gql`. Файл генерируется, вручную его не правят. Он хранится в Git, чтобы контракт API был виден без запуска приложения.

В задании редактор запросов — Apollo Sandbox. В текущей версии Nest по умолчанию открывается GraphiQL, поэтому он выключен, а Sandbox подключён плагином `ApolloServerPluginLandingPageLocalDefault`.

Поле списка опыта в схеме называется `experience`, как в примере из задания. В Prisma связь называется `experiences`, потому что это набор строк таблицы `Experience`.

Корневой запрос `profile` читает одну строку профиля. Навыки, опыт, проекты и ссылки загружаются отдельными методами и только если клиент указал соответствующее поле. Запрос имени и описания не открывает остальные таблицы. Для одной визитки этого достаточно: родитель один, пакетировать запросы через DataLoader не требуется.

### Подготовка базы при старте

Миграции описывают структуру таблиц и лежат в `prisma/migrations`. В контейнере перед запуском Node выполняется `prisma migrate deploy`: команда применяет уже созданные миграции и не задаёт вопросов в терминале.

Данные записывает `ProfileSeedService` после установки соединения. Сервис считает строки `Profile`. Если строка уже есть, запись пропускается. Поэтому перезапуск не дублирует визитку, а пустая база заполняется сама.

Клиент Prisma генерируется при сборке образа в `src/generated/prisma`. Каталог не коммитится: его содержимое полностью определяется `schema.prisma`.

### Docker

В Compose два контейнера. Образ приложения собирается из `Dockerfile`. Postgres берётся готовым образом `postgres:16`.

Приложение ждёт, пока `pg_isready` подтвердит, что база принимает соединения. Иначе миграции стартовали бы раньше сервера.

Адрес базы зависит от того, где запущен процесс. В Compose хост называется `postgres`, порт внутри сети — `5432`. С компьютера та же база доступна как `127.0.0.1:5432`. Имя пользователя, пароль и имя базы совпадают. Логин `postgres` и пароль `postgres` — учебные данные для локального Compose, не секрет боевого окружения.

На Render база — отдельный управляемый PostgreSQL, не контейнер из Compose. Приложение получает её адрес через `DATABASE_URL` окружения хостинга. Значение из `Dockerfile` остаётся адресом для локальной сети Compose.

Образ приложения — официальный `node:24-bookworm-slim`. Предупреждения сканера относятся к пакетам этого образа.

Приложение собрано как ES-модули (`"type": "module"`). Импорты в исходниках используют расширение `.js`, потому что его ожидает Node после компиляции TypeScript.
